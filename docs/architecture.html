Boot sequence

  1. Serial and preferences (needed for the RS485 pins).
  2. Modbus first: the operator scans for its slave right after power-on – the bridge has to answer before anything slow (Wi-Fi, sensors) starts. The Modbus task then runs independently on core 1.
  3. Status LED, debug flag, reset-button interrupt, Wi-Fi/MQTT reconnect timers, access point.
  4. Crash check: after a panic or watchdog reset all sensors are disabled and the ESP restarts.
  5. Sensors and digital I/O are initialised before MQTT, so discovery knows which entities exist.
  6. Wi-Fi connect, MQTT/sensor/I/O tasks, HTTP routes, OTA, server start.

Hörmann protocol

The operator is the Modbus RTU master; the bridge registers as slave ID 2 during the bus scan (UART2, 57600 baud, 8 data bits, even parity, 1 stop bit).

RegisterDirectionContent
0x9C41master writesCommand counter / request
0x9CB9master readsResponse: the "key presses" of the bridge (command registers +2/+3), bus-scan identification
0x9D31master broadcasts+1 position (low byte current, high byte target, value/200), +2 state, +6 light

A command is a simulated key press: the start value is returned on the next poll, the end value 100 ms later. Only one command can be pending at a time.

State byteStateDetailed state
0x01OPENINGopening
0x02CLOSINGclosing
0x05MOVE_HALFopening h
0x09MOVE_VENTINGopening v
0x0AVENTventing
0x20OPENopen
0x40CLOSEDclosed
0x80HALFOPENopen h
0x00STOPPED (or VENT, see below)stopped
  • Vent workaround: some operators never report 0x0A. A stopped door at position 0x08 (current = target) is therefore treated as VENT.
  • Light: on when the light byte is 0x10 or 0x14.
  • Set position: the bridge starts an open or close movement and sends stop once the reported position passes the target.

Preference registry

All settings are defined once in PREF_REGISTRY[] (preferences_handler.h): key (max. 15 characters), type, redacted flag, group and default. The registry drives first-boot defaults, GET /config and saving.

  1. Add #define preference_xxx "key".
  2. Add a row to PREF_REGISTRY[] with type, group (BASIC, SENSOR, IO, EXPERT or INTERNAL) and default.
  3. Add the form field with id and name = key to index.html.
  4. Read it with prefs->getString/getInt/getDouble/getBool(preference_xxx).
Check boxes need one extra lineHTML forms send "on" or nothing, so the generic save loop skips all BOOL preferences. Every new boolean must be added to the checkbox() handling in PreferenceHandler::saveConf(), otherwise it is never saved.

Web interface build

The web interface is a single file, WebUI/webpage/index.html, without external resources (the bridge often runs without internet access). Before every build the PlatformIO pre-script compress.py minifies HTML and JavaScript (htmlmin, jsmin), compresses it with zlib level 9 and writes WebUI/index_html.h. The ESP serves it with Content-Encoding: deflate.

  • Keep element IDs and name attributes in sync with the preference keys.
  • htmlmin removes whitespace between tags – use CSS gaps instead of spaces between inline elements.
  • Avoid JavaScript template literals; jsmin is conservative ES5-style.
  • The garage scene is inline SVG coloured via CSS variables, so light and dark mode work without extra assets.

Building, CI and releases

cd HCPBridgeESP32
pio run                        # all default environments
pio run -e HCP_Giffordv3       # one board
ls fw/                         # <env>-v<version>.bin
  • test Build (manual workflow) builds all default environments.
  • Build and release runs on every push to master that touches firmware files (changes under docs/, .github/, tools/ and *.md are ignored). It reads HA_VERSION from configuration.h, uses it as tag and release name and attaches fw/*.bin.
  • Bump HA_VERSION (and the version in esphome_hcpbridge.yaml) for every release.

Contributing

  1. Fork the repository and create a feature branch.
  2. Keep changes in the existing structure: one manager per concern, settings through the registry.
  3. If a feature also makes sense for the ESPHome variant, add a matching (commented) block to esphome_hcpbridge.yaml.
  4. Update the documentation in docs/ and open a pull request with a clear description.

Editing this documentation

The site is plain HTML in /docs, published by GitHub Pages from the master branch – no build step, no dependencies. Shared styles live in docs/assets/style.css; the navigation, the "On this page" list and the copy buttons are generated by docs/assets/site.js. To add a page, copy an existing page, replace the content inside <main> and add one line to the NAV list in site.js. docs/.nojekyll makes GitHub serve the files unchanged.
